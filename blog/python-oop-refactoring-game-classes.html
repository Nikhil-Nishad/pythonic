Mastering Python OOP: Refactoring a Procedural Game into Clean, Modular Classes

Anyone can define a Python class. Understanding why and how to separate responsibilities, encapsulate mutable state, and eliminate global variables is what transforms hobbyist scripts into production-ready software.

1. The Procedural Nightmare: Global Variable Spaghetti

When most programmers start building a game, they write everything in a single, top-level procedural script. It starts small:

# ❌ The Procedural Trap (Global State Spaghetti)
snake_x = 10
snake_y = 10
direction = "RIGHT"
food_x = 5
food_y = 5
score = 0

def move():
    global snake_x, snake_y
    if direction == "RIGHT": snake_x += 1

Now imagine you want to add a second player, or an autonomous A* AI rival bot. Do you duplicate snake2_x, snake2_y, direction2? What about unit testing your collision logic without booting Pygame? With global state, your architecture collapses.

2. Domain Modeling: Identifying Entities and Responsibilities

To refactor this into Object-Oriented design, we apply the Single Responsibility Principle (SRP) and divide the system into clean domain boundaries:

  • Vec2 (Value Object): Represents an immutable coordinate $(x, y)$ on the grid.
  • Snake (Entity): Owns its body coordinates, current direction, and growth state.
  • Food (Entity): Owns its position and value.
  • GameEngine (Orchestrator): Glues entities together, checks collisions, and manages the main loop.

3. Step 1: Modeling Value Objects with `@dataclass`

Coordinates should be immutable value objects. In Python 3.7+, dataclasses make this effortless:

from dataclasses import dataclass

@dataclass(frozen=True)
class Vec2:
    x: int
    y: int

    def __add__(self, other: "Vec2") -> "Vec2":
        return Vec2(self.x + other.x, self.y + other.y)

# Standard directions defined as immutable constants
UP = Vec2(0, -1)
DOWN = Vec2(0, 1)
LEFT = Vec2(-1, 0)
RIGHT = Vec2(1, 0)

4. Step 2: Encapsulating Snake State in a `Snake` Class

The Snake class now encapsulates its own movement and body queue without any reference to Pygame, rendering, or global scores:

from collections import deque
from typing import Set

class Snake:
    def __init__(self, start_pos: Vec2, initial_length: int = 3):
        self.body: deque[Vec2] = deque([
            Vec2(start_pos.x - i, start_pos.y) for i in range(initial_length)
        ])
        self.direction: Vec2 = RIGHT
        self.next_direction: Vec2 = RIGHT

    @property
    def head(self) -> Vec2:
        return self.body[0]

    def steer(self, new_dir: Vec2) -> None:
        # Disallow reversing directly into itself
        if (new_dir.x != -self.direction.x) or (new_dir.y != -self.direction.y):
            self.next_direction = new_dir

    def step(self, grow: bool = False) -> Vec2:
        self.direction = self.next_direction
        new_head = self.head + self.direction
        self.body.appendleft(new_head)
        if not grow:
            self.body.pop()
        return new_head

    def check_self_collision(self) -> bool:
        # Head collides if it appears anywhere else in body
        return self.head in list(self.body)[1:]

5. Step 3: Managing Collectibles with a `Food` Class

import random
from typing import Container

class Food:
    def __init__(self, grid_w: int, grid_h: int):
        self.grid_w = grid_w
        self.grid_h = grid_h
        self.position = Vec2(0, 0)

    def respawn(self, occupied: Container[Vec2]) -> Vec2:
        while True:
            candidate = Vec2(random.randint(0, self.grid_w - 1),
                             random.randint(0, self.grid_h - 1))
            if candidate not in occupied:
                self.position = candidate
                return self.position

6. Step 4: The `GameEngine` Orchestrator

Now the main engine acts as an event coordinator rather than a messy dumping ground:

class GameEngine:
    def __init__(self, width: int = 30, height: int = 30):
        self.width = width
        self.height = height
        self.snake = Snake(Vec2(width // 2, height // 2))
        self.food = Food(width, height)
        self.food.respawn(self.snake.body)
        self.score = 0
        self.is_game_over = False

    def tick(self) -> None:
        if self.is_game_over:
            return

        will_eat = (self.snake.head + self.snake.next_direction) == self.food.position
        new_head = self.snake.step(grow=will_eat)

        # Check wall boundary
        if not (0 <= new_head.x < self.width and 0 <= new_head.y < self.height):
            self.is_game_over = True
            return

        # Check body self-collision
        if self.snake.check_self_collision():
            self.is_game_over = True
            return

        if will_eat:
            self.score += 10
            self.food.respawn(self.snake.body)

7. The Huge Payoff: Testability, AI Bots & Multiplayer

Look at what we achieved through this clean OOP refactoring:

  1. Headless Automated Unit Testing: You can test game rules in pytest without ever initializing a GUI window or Pygame instance.
  2. Multiplayer & Bot Injection: You can instantiate bot_snake = Snake(...) and have an AI steer it independently on the same grid.
  3. Framework Agnostic: You could swap Pygame for a WebSockets server, Tkinter, or a console renderer without touching a single line of Snake or GameEngine logic.

8. Frequently Asked Questions

What is the advantage of `@property` on the head attribute?

Using @property allows callers to read snake.head like an attribute, while preventing external code from accidentally assigning a new value to it directly (e.g. snake.head = (5, 5)), maintaining encapsulation.

Should I use inheritance or composition in game design?

Prefer composition over inheritance. Notice how GameEngine owns a Snake and a Food object rather than inheriting from them. This keeps relationships flexible and avoids rigid class hierarchies.
